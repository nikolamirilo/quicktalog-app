Read this first

Six things are true today that PROD_RUNBOOK.md does not know, because the repo moved on after it was written. Each one changes what you do.

1. The go/no-go check in PROD_GUIDE.md is blind

grep -c '|f$' cannot match psql's default output, which puts a space after the pipe. Measured against the recorded TEST verify file, which contains one genuine failure:

CommandReturnsMeans
grep -c '|f$' verify.txt0"all clear" — wrong
grep -cE '\| f$' verify.txt1the real failure

So the documented gate reads pass whether or not a check failed. Run psql with -A -F '|' (the form rehearsal.test.ts uses), or use the corrected pattern. Read the tables by eye as well — never trust a bare count.

2. The cutover SQL cannot run on PROD at all yet

preflight.sql, remap-user-ids.sql, verify.sql and rollback-remap.sql were all rewritten on 2026-09-29 against the renamed schema — ai_credits, catalogue_subscribers, catalogues.user_id, analytics.pageviews. Those names arrive in migration 21, 20260929120000_schema_consistency. Against PROD today the very first command dies with 42P01, printing almost nothing, so an empty-looking preflight-t3.txt is the symptom.

Migration 21 is a hard prerequisite of every cutover script. That is why step 1.9 comes before the rehearsal on TEST and before the dark import.

3. It is 19 pending migrations, not 13

The runbook header says "migration 3 of 16". Six more have landed since: the AI credits ledger, the category/container merge, the credit-limit binding, the business-type backfill, the schema renames and the acquisition-source column. supabase db push has no --target, so one invocation applies all 19 in filename order, M00 included, with no pause for the audit, the app_rls password, the terms_version row or a deploy.

4. The old deployed code and the new code need opposite schemas

Migration 5 (M00) turns on RLS and revokes anon, which breaks whatever is deployed on PROD now — it still serves 2163 catalogue reads a day through /rest/v1. The current code needs migration 21's renames. One comes before the other, so the migrations and the deploy have to happen together, in one short maintenance window. That is step 1.9, and it is the one part of Phase 1 users can see.

5. Two commands in the repo do not do what they look like
  • npm run test:db fails before running anything. tests/db-pglite/tools/extract-plan.mjs reads .claude/plans/active/supabase-auth-migration/PLAN.md; the folder is 2026-09-15-supabase-auth-migration. With set -e in run.sh, the whole 692-scenario gate aborts on ENOENT.
  • Every import and rollback-push line in PROD_GUIDE.md omits ALLOW_PROD=1, which scripts/lib/guard.ts hard-refuses: refusing to touch PROD without ALLOW_PROD=1. PROD_RUNBOOK.md has it right.
6. .env.cutover silently ignores four of the secrets

scripts/cutover/config.ts copies exactly six names out of that file: MIGRATION_DATABASE_URL, DB_ADMIN_CONNECTION_STRING, DB_CONNECTION_STRING, SUPABASE_SECRET_KEY, CLERK_SECRET_KEY, SUPABASE_ACCESS_TOKEN. SUPABASE_SMTP_PASS, SUPABASE_CAPTCHA_SECRET and the two SUPABASE_GOOGLE_* values never reach the process — export them in the shell instead, or auth-config.ts --apply drops them while still switching captcha on.

The two phases

The boundary is the re-key. Before it, every user still signs in through Clerk and every step can be undone. After it, 2171 user ids have changed and the only way back is a scripted rollback inside a closing window.

Phase 1 · preparation

Reversible. Your pace.

Twelve steps. Do them in order, one evening at a time, over as many days as you like. Clerk keeps serving traffic throughout and nobody has to sign in again. Stop whenever you want and the site is fine.

User impactNone, except the one short window in step 1.9
UndoEvery step except 1.9's schema change — take its dump
Ends withDormant Supabase identities and a green go/no-go list
Phase 2 · the window

One way. Finish it.

Sixteen steps, about 90 minutes, roughly 35 of them with writes frozen. From the re-key onward the user ids are uuids and rollback is a scripted procedure with a deadline, not an undo. Book the time, clear the evening, do not start it tired.

User impactMaintenance page, then one forced sign-in each
UndoScripted rollback only — config-only before the re-key, then 72h at the outside
Hard gatesPreflight, V12 passwords, the smoke list

Sequence in one line. Close the hole → audit it → ask Clerk for the export → rehearse the whole thing locally on a copy of real data → configure PROD → migrate and deploy in one short window → rehearse on TEST → dark-import the users → then the cutover window.

STEP 2.9 · target < 60s

The re-key — this is the one-way step

One transaction. It takes ACCESS EXCLUSIVE on public.users before any precondition read, so there is no lock upgrade. It disables exactly three named triggers, snapshots counters into migration.pre_remap_counts, rewrites the ids, asserts nothing changed hands, and appends to migration.cutover_log.

Irreversible
Session pooler on 5432 or direct — never 6543, it runs transactions
time psql "$MIGRATION_DATABASE_URL" -v ON_ERROR_STOP=1 \
     -f scripts/cutover/remap-user-ids.sql
How to read what happens
  • It must end with COMMIT.
  • Lock timeout (it sets 5s): terminate the blockers and retry once.
  • Any other exception: the whole transaction rolls back, no user is affected. Stop and diagnose — do not retry blind.
  • Seven preconditions can refuse it. Only four are pre-checked by preflight; two are not pre-checked at all — a target uuid already present in public.users, and map rows marked migrated with no auth.users row.
Immediately after: prove the ON UPDATE CASCADE fired
psql "$MIGRATION_DATABASE_URL" \
 -c "select count(*) filter (where id like 'user\_%') as clerk_left,
            count(*) filter (where id ~ '^[0-9a-f]{8}-') as uuid_now
       from public.users" \
 -c "select count(*) from public.catalogues c
      where not exists (select 1 from public.users u where u.id = c.user_id)"

The second query must be 0. A non-zero result means the cascade did not fire, and you have found a real bug at the worst possible moment.

If it goes wrong

In order. rollback-remap.sql refuses to start until step 3 has run, and that refusal is the one that will surprise you at 2am.

  1. Maintenance on, sign-ups off, worker paused.
  2. Snapshot verify.sql so you know the state you are leaving.
  3. Before the push: check migration.auth_user_deletions. The push script's third phase calls Clerk's deleteUser for every row in that table and counts a 404 as success. One stale or wrong row permanently erases a Clerk account nobody asked to erase. Confirm every clerk_user_id in it is a genuine erasure request first.
  4. Carry back anyone who signed up during the window. rollback-remap.sql refuses while any uuid-keyed user has no migrated map row, with uuid users without a Clerk id: run push-supabase-users-to-clerk.ts first.

  5. psql ... -f scripts/cutover/rollback-remap.sql — it drops users_id_is_uuid, disables and re-enables the same three triggers, and re-keys back through the map.
  6. Clerk sign-up public again, webhook back on.
