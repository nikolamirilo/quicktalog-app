# Database call-site inventory

> Phase-1 report produced on 2026-09-16 while preparing `../PLAN.md`. It reflects branch `test` at `fcee862` and read-only queries on the TEST project. Where it disagrees with `../PLAN.md`, the plan wins.

I found 68 places in quicktalog-app that read or write the database (listed below). Everything else in the app reaches the data through one of them.

**Two ways into the database**
- **Drizzle** (utils/drizzle.ts:7): connects over DB_CONNECTION_STRING as the `postgres` role, which has BYPASSRLS. Every Drizzle call ignores RLS completely. Turning RLS on changes nothing for these calls unless each request runs inside a transaction that does `SET LOCAL ROLE authenticated` plus `set_config('request.jwt.claims', ...)`. That transaction is required because the pooler is in transaction mode with prepare:false.
  - Used by: actions/catalogue.ts, newsletter.ts, qr-configs.ts, themes.ts; lib/ai/access.ts; lib/users/fetchUserData.ts; api/dashboard/catalogues; api/dashboard/newsletter.
- **supabase-js** (utils/supabase/server.ts): uses the publishable key, so it runs as `anon`. No Supabase session ever exists.
  - Used by: api/items and api/items/[name]; api/dashboard/analytics; the Clerk webhook (syncFromClerk.ts:142/171, actions/users.ts:83); the Paddle webhook (process-webhook.ts, 8 queries); the on-demand user sync in fetchUserData.ts:55.

**Not found anywhere:** `.rpc()`, `.storage`, `supabase.auth`, `drizzleClient.execute` or `.transaction`, and any browser Supabase client. Raw SQL appears only in tests/e2e/helpers/cleanup.ts. tests/unit/server_actions/ai.test.ts mocks drizzleClient and makes no real calls.

**Who sees the publishable key.** NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY are referenced only in utils/supabase/server.ts:7-8,24-25. That file is marked "use server" and no "use client" module imports it, so the key is not inlined into client bundles today. It is also set in CI (.github/workflows/ci.yaml:52-53). Publishable keys are public by design, so treat it as public. Anyone holding it can call PostgREST directly with these grants (confirmed read-only on TEST):
- **users:** SELECT, INSERT, UPDATE, DELETE
- **catalogues:** SELECT, INSERT, UPDATE
- **subscriptions:** SELECT, INSERT, UPDATE
- **analytics:** SELECT, INSERT
- **newsletter:** SELECT
- **job_logs:** INSERT
- **get_pageview_totals:** EXECUTE. It is declared to return uuid while analytics.user_id is text, so it is probably broken.

**Stale grants.** The lockdown migration justifies several grants with files that no longer exist: app/api/analytics/route.ts, app/api/analytics/all/route.ts, app/api/subscriptions/check/route.ts and utils/paddle/get-customer-id.ts (removed in commits 4a2f481 and ea8fbfa). Nothing in the app today needs anon INSERT/UPDATE on catalogues, anon INSERT on analytics or job_logs, anon SELECT on newsletter, or EXECUTE on get_pageview_totals.

**Caches that must not hold per-user sessions**
1. **Redis mirror** (key = catalogue name, value = the full row including createdBy).
   - Written by createCatalogue, updateCatalogue (unsaved builder state, with no database write), publishCatalogue and updateItemStatus.
   - Filled on read by getCatalogueByName and deleted by deleteItem. deleteMultipleItems never removes keys.
   - Read by the preview page, the admin builder and QR-editor pages (which check ownership against the Redis `createdBy`), and DashboardItem.
2. **Next data cache and ISR for public catalogue pages.** app/catalogues/[name]/page.tsx has revalidate=86400 and generateStaticParams. Its fetches to /api/items and /api/items/[name] carry tags catalogues-list, catalogue-${name}, catalogue-metadata and catalogue-detail. app/sitemap.ts uses force-cache.
3. **Invalidation.** helpers/server.ts calls revalidateTag/revalidatePath, including revalidatePath('/', 'layout'). It is exposed publicly through GET /api/revalidate.
4. **Browser only:** SWR in hooks/useDashboardData.ts.

The public catalogue fetches run at build or ISR time, so they need an anon policy that allows only status='active'. They cannot use a user session.

**Access model once RLS is on**
- **Signed-in owner:** the catalogue, theme, QR-config and dashboard operations, plus prompt metering.
- **Public read:** only catalogues with status='active'.
- **Narrow public write:** the newsletter and product newsletter signups.
- **Privileged (service role):** the Clerk and Paddle webhooks, the on-demand user sync (it writes plan_id and customer_id), checking whether a slug is taken across all users, the user-deletion cascade and the e2e cleanup.

Foreign-key cascades ignore RLS, so deleting a user with the service role still removes everything they own.

**Most serious problems today**
- **The anon grants alone are the worst.** With the key, anyone can change users.plan_id to get paid features, delete or rename any user id to take over or wipe accounts, deface or take any catalogue, and dump every user's and subscriber's email.
- **User data leaks without sign-in.** GET /api/users/[id] and the getUserData(userId) server action both return any user's email, plan and customer_id. User ids are easy to collect from /api/items and from every public catalogue's HTML.
- **Drafts are public.** The getCatalogueByName server action has no auth, and /catalogues/[name]/preview shows drafts and unsaved edits to anyone.
- **Other gaps:**
  - upsertQrConfig has no auth.
  - newsletterSignup accepts ownerId and catalogueId from the browser.
  - publishCatalogue writes the whole browser payload back, so an owner can reassign created_by.
  - updateItemStatus does not tie `name` to `id`, so it can rewrite another catalogue's Redis entry.
  - /api/revalidate needs no auth.

## open questions
- Which identity will RLS policies key on? auth.users is empty and users.id holds Clerk ids. Options: Supabase third-party auth with Clerk (auth.jwt()->>'sub' = users.id), or migrating to Supabase Auth. The choice decides how Drizzle calls (postgres, BYPASSRLS, transaction-mode pooler) get a per-request role and claims: SET LOCAL ROLE authenticated plus set_config('request.jwt.claims') inside a transaction.
- Should the Redis catalogue mirror stay a shared, privileged cache? It is filled from full DB rows, trusted for ownership (createdBy) on the builder and QR-editor pages, and served without auth on /preview. Per-user RLS cannot fill it safely.
- Is the Vercel production deployment on this commit? The lockdown migration cites routes that were removed (app/api/analytics, app/api/analytics/all, app/api/subscriptions/check, utils/paddle/get-customer-id.ts). Check PROD PostgREST logs for anon traffic (app, worker, or anything else) before revoking those grants.
- Does quicktalog-backend's subscriptionProcessingJob or analyticsProcessingJob read subscriptions or analytics in a way that anon-forged rows could affect (e.g. setting plan_id)? It uses service_role, so it is unaffected by RLS, but its inputs are anon-writable today.
- Is get_pageview_totals still called anywhere (worker, edge function)? It declares user_id uuid while analytics.user_id is text, so it likely errors. Can EXECUTE for anon be revoked?
- Is there a unique constraint on newsletter (catalogue_id, email) and on product_newsletter.email? Without one, the SELECT-then-INSERT dedupe cannot become an anon-safe INSERT ... ON CONFLICT DO NOTHING.
- Should public catalogue payloads include created_by? It is currently in every public page's HTML (needed only for newsletter owner_id, which the server should derive instead). A column-restricted public view or anon column grants would remove it.
- Slug-availability checks (actions/catalogue.ts:151, :187 and hooks/useCatalogueName.ts:91) need to see all users' catalogues, drafts included. Should they become a SECURITY DEFINER slug_available(text) RPC, or rely on the catalogues_name_key unique violation?
- Is a users.email unique constraint intended? handleCustomerData updates every row matching an email.
- Which DB_CONNECTION_STRING does tests/e2e/helpers/cleanup.ts use in CI, and is it guaranteed never to be PROD? It deletes by slug prefix across all users as postgres.
