# Where the Clerk user id lives

> Phase-1 report produced on 2026-09-16 while preparing `../PLAN.md`. It reflects branch `test` at `fcee862` and read-only queries on the TEST project. Where it disagrees with `../PLAN.md`, the plan wins.

## Where the Clerk user id lives outside `users.id` (app, backend, packages)

### Bottom line
- **No third-party system holds the Clerk id.** Paddle gets only an email, and a customer is linked by `customer_id`. PostHog has no `identify`, Sentry has no `setUser`, Microsoft Clarity and GTM are anonymous. UploadThing uses a fake auth id and matches files by key only.
- **In the database, the Clerk id sits only in `users.id` and 6 FK columns**, all `text` with `ON UPDATE CASCADE ON DELETE CASCADE` (checked on TEST): `catalogues.created_by`, `analytics.user_id`, `newsletter.owner_id`, `ocr.user_id`, `prompts.user_id`, `user_themes.user_id`.
- **Read-only checks on TEST found no Clerk id in any jsonb or text payload:**
  - 3 users, all ids in `user_*` format; `auth.users` = 0; `auth.identities` = 0.
  - A scan of every text, jsonb and array column in `public` found `user_` only in `users.id` (3), `catalogues.created_by` (3), `prompts.user_id` (2) and `user_themes.user_id` (1). `catalogues.metadata`, `content`, `legal`, `appearance`, `contact`, `header`, `footer`, `partners` and `tags` = 0; `users.cookie_preferences` and `consents` = 0; `qr_configs.config` = 0; `job_logs.log` = 0.
  - `net._http_response`, `net.http_request_queue` and `cron.job_run_details` = 0. Storage objects = 0. Vault secrets = 0, so the webhook triggers do nothing on TEST.
- **The dangerous copies are outside Postgres and outside FK cascade:**
  1. **Upstash Redis values.** Keys are catalogue slugs, but values are the full catalogue JSON including `createdBy`.
  2. **The Next data cache / ISR of public catalogue pages** (full row including `created_by`).
  3. **Client state.** `CatalogueContext` sets `createdBy` from the Clerk `user.id`.
  4. **Clerk itself.** `publicMetadata.cookieConsent` is the source of truth for signed-in users, and `users.image` points at the Clerk CDN (3 of 3 TEST rows).
  5. **External CRM / Brevo** via a trigger payload `to_jsonb(new)` sent to PROD edge functions, whose code is in no repo.
  6. **The backend job's URL** `${APP_URL}/api/users/${user.id}`.
  7. **Logs:** Vercel/Cloudflare console logs, and Sentry request cookies (`sendDefaultPii: true`).
- **Two write-back paths would put a stale Clerk id back into the DB after a remap:**
  - `publishCatalogue` spreads the client- or Redis-supplied `createdBy` into `UPDATE catalogues` (`actions/catalogue.ts:337-347`, fed from Redis by `DashboardItem.tsx:40-62`).
  - `newsletterSignup` takes `ownerId` from the public page payload (`CatalogueFooter.tsx:42-46`).
- **Ownership gates on the builder and QR-editor pages read `createdBy` from Redis, not the DB** (`builder/page.tsx:11-19`, `qr-editor/page.tsx:16-24`). Every owner gets a 404 after a remap until Redis is flushed or rewritten.

- **E2E:** Clerk testing token plus `E2E_CLERK_USER_*` secrets. The test account must exist with a 1-catalogue plan. Cleanup is by slug.

### Schema, packages and migration systems
- **`../quicktalog-packages/src/drizzle/migrations/schema.ts` is generated by `drizzle-kit pull`**, which runs in `.husky/pre-commit` when `DB_CONNECTION_STRING` is set. It is not the source of truth.
  - Every user-referencing column is `text`: `users.id` (:25), `prompts.userId` (:9, nullable), `newsletter.ownerId` (:53), `ocr.userId` (:66, nullable), `analytics.userId` (:92), `userThemes.userId` (:129), `catalogues.createdBy` (:162).
  - It declares a `pgPolicy` on `users` (:35) that does **not** exist in the DB.
  - It is missing CASCADE on `analytics_user_id_fkey` (:95-99), has the wrong FK name `catalogues_created_by_fkey` vs the real `catalogues_new_created_by_fkey`, and is missing `users_customer_id_key`, the `subscriptions` FKs and `prompts_service_catalogue_key`.
  - `relations.ts` is not exported (`src/drizzle/index.ts:1` exports only `schema`). No roles are declared.
- **`supabase/migrations/` in the app is what is actually applied.** TEST `supabase_migrations.schema_migrations` lists exactly the 4 app migration files.
  - The app's `drizzle.config.ts` points at a non-existent `./drizzle/schema.ts`, and `docs/guides/drizzle.md` is just 4 commands, so drizzle-kit generate/push is unused.
  - In packages, `drizzle.config.ts` also points at a non-existent `src/drizzle/schema.ts`, and `0000_goofy_raza.sql` is an all-commented introspection dump.
- **Release flow for a schema change:**
  1. Apply a SQL migration via `supabase/migrations`.
  2. In packages, re-pull (pre-commit), then `npm run release` (`npm version minor` + `git push --follow-tags`).
  3. `.github/workflows/publish.yaml` publishes on push to `main` via OIDC if the version is new.
  4. Bump consumers. The app wants `^1.54.0` and has 1.54.0 installed; the backend wants `^1.42.0` but its lockfile has **1.51.0** (lagging).
  - Note: `.husky/pre-push` runs `npm version minor`, which contradicts the README ("no pre-push hook").
- **TypeScript impact:** `User` = `InferSelectModel<users>` (`src/types/general.ts:79-87`) and `Catalogue` (`src/types/catalogue.ts:13`). A Drizzle `uuid()` column also infers `string`, so switching text→uuid causes no TS breakage, only runtime `22P02` errors on non-UUID input.
- **DB objects that depend on the id:**
  - Views `contacts` (`id = COALESCE(u.id, gen_random_uuid()::text)`, joins `created_by = u.id`) and `active_subscriptions` (joins `created_by = u.id`). They block `ALTER COLUMN TYPE` (checked on TEST).
  - Trigger `Brevo New Contact Webhook`: AFTER INSERT/UPDATE on `users`, posts `to_jsonb(new)` to the **PROD** edge function URL.
  - `get_pageview_totals` returns `user_id uuid` while `analytics.user_id` is text. Calling it on TEST raises 42804 "Returned type text does not match expected type uuid". It has no callers in any repo and still grants EXECUTE to anon. This suggests ids were once UUIDs.
  - `analytics_upsert_trigger` is already dropped on TEST. Its state on PROD is unknown; if present, a cascaded UPDATE would double analytics counters.

### Input for the id-strategy decision (not final)
- **A) Keep `users.id` as text, holding the UUID string.**
  - Pros:
    - No ALTER TYPE, and no view drop/recreate.
    - An in-place `UPDATE users SET id=...` cascades to all 6 children.
    - The Drizzle package needs no functional change.
  - Cons:
    - An FK to `auth.users(id)` is impossible (text≠uuid), so there is no automatic ON DELETE CASCADE. It needs a trigger to replace the Clerk `user.deleted` webhook.
    - Every policy needs `(select auth.uid())::text`.
    - The DB will not reject a stale Clerk id written back by `publishCatalogue`, `newsletterSignup` or Redis.
    - Old and new id formats can coexist silently.
- **B) Convert to the `uuid` type (my lean).**
  - Pros:
    - `REFERENCES auth.users(id) ON DELETE CASCADE`, plus an `auth.users` insert trigger to create the `public.users` row. This removes the webhook and the on-demand-sync race in `lib/users/fetchUserData.ts:46-74`.
    - Policies need no casts.
    - Stale Clerk ids fail loudly instead of silently re-owning rows.
    - It fixes `get_pageview_totals`, and TS types are unchanged.
  - Cons:
    - Two-phase migration: remap values, then drop 6 FKs and 2 views, `ALTER TYPE ... USING id::uuid`, and recreate them.
    - Requires re-pull and a new package publish, with the backend upgraded from 1.51.
    - Any leftover caller passing a Clerk id errors (500 instead of 404), e.g. the backend job hitting `/api/users/{id}` mid-cutover.
- **C) Keep the Clerk id and add `auth_user_id uuid`.**
  - Pros:
    - No child-row, Redis, ISR or CRM rewrite; easy rollback.
    - Log and CRM correlation stays stable.
  - Cons:
    - Every RLS policy needs a users lookup or a SECURITY DEFINER helper.
    - New signups have no Clerk id, so a synthetic text id must be minted anyway, leaving the format mixed forever.
    - About 40 ownership comparisons need a per-request id translation.
    - Clerk ids stay publicly exposed via `created_by`.
    - Two identifiers must be kept in sync permanently.
- **Whichever option is chosen, the cutover needs:**
  - Pause the worker cron.
  - Disable the `users` Brevo trigger during the remap.
  - Verify `analytics_upsert_trigger` is gone on PROD.
  - Flush or rewrite Redis values.
  - Call `/api/revalidate` or redeploy.
  - Strip `createdBy`/`id` from `publishCatalogue`'s SET, and derive `newsletter.owner_id` server-side.
  - Migrate Clerk `cookieConsent` and image URLs.
  - Recreate the E2E user.
  - Move the Paddle webhook and user-sync writes off the `anon` role before enabling RLS: `utils/paddle/process-webhook.ts:62-223` and `app/api/clerk/route.ts:51` use the publishable-key client.
