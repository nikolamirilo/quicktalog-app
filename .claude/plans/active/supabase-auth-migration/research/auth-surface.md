# Clerk authentication surface

> Phase-1 report produced on 2026-09-16 while preparing `../PLAN.md`. It reflects branch `test` at `fcee862` and read-only queries on the TEST project. Where it disagrees with `../PLAN.md`, the plan wins.

## 0. Summary
- **What imports Clerk.** 21 app files and 4 test files import from `@clerk/*`. The only packages used are `@clerk/nextjs`, `@clerk/nextjs/server`, `@clerk/nextjs/webhooks` and `@clerk/testing/playwright`. Installed versions: `@clerk/nextjs` 6.39.3 (package.json:21) and `@clerk/testing` 2.0.34 (package.json:111). Nothing imports `@clerk/themes`, `@clerk/types` or `@clerk/backend`.
- **Clerk APIs in use.** `clerkMiddleware`, `createRouteMatcher`, `auth.protect()`, `auth()`, `currentUser()`, `clerkClient().users.getUser/updateUserMetadata`, `verifyWebhook`, `ClerkProvider`, `SignIn`, `SignUp`, `UserButton`, `SignOutButton`, `UserProfile` and `useUser`. The tests also use `clerkSetup`, `setupClerkTestingToken` and `clerk.signIn`.
- **Not used anywhere** (grep found nothing):
  - `useAuth`, `useClerk`, `useSession`
  - `SignedIn`, `SignedOut`, `SignInButton`, `SignUpButton`, `RedirectToSignIn`
  - `getToken`, `sessionClaims`, `has()`, roles or permissions
  - organizations, JWT templates, impersonation
  - `unsafeMetadata`, `privateMetadata`

  The database never sees a Clerk token. Every query runs as `postgres` (Drizzle) or `anon` (supabase-js). The only metadata key in use is `publicMetadata.cookieConsent`.
- **What the server needs from a session.** 20 of the 21 server-side reads only need `user.id`. Profile fields (emailAddresses[0], firstName, lastName, imageUrl, publicMetadata) are read in only 3 places:
  - `actions/users.ts:15-27` and `app/api/users/[id]/route.ts:16-27`, both only to create a missing `public.users` row.
  - `components/navigation/AuthLinks.tsx:63-65`, for the display name.

  Everything else in the UI reads the profile from `public.users` through `getUserData` → `fetchUserData`.

## 3. Route protection
- **Middleware** (middleware.ts:1-14): `clerkMiddleware` runs on every non-static path, including `/api/*`, `/monitoring` (the Sentry tunnel) and `/ingest/*` (the PostHog rewrite). Only `/admin(.*)` is protected (:3,6).
- **Page-level checks:**
  - `/admin/dashboard` has no redirect. When `getUserData()` returns null it shows "Something went wrong" (app/admin/dashboard/[[...rest]]/page.tsx:16-28).
  - `/admin/[name]/builder` and `/qr-editor` check ownership against a catalogue read Redis-first, and call `notFound()` on failure.
  - **`/admin/[name]/analytics` checks nothing.**
  - `/admin/checkout/success` is static.
  - `/catalogues/[name]/preview` sits outside /admin, has no auth, and serves drafts from Redis.
- **API routes that check auth:** dashboard/catalogues, dashboard/analytics, dashboard/newsletter, update-consent, agent (via `authorize`), and users/[id] (only partly).
- **API routes with no auth:** items, items/[name], items/uploadthing (its auth is a stub), pdf, revalidate. The clerk and paddle webhooks use signature checks.
- **Server actions that check nothing:** `getUserData(userId)`, `upsertQrConfig`, `getQrConfig`, `getCatalogueByName`, `newsletterSignup`, `productNewsletterSignup`, `sendContactEmail`.

**What Supabase needs:** middleware that refreshes the session and redirects `/admin` to `/auth?next=`, preferably verifying with `getClaims()` so each request doesn't call the Auth server. Add `requireUser()` redirects in the admin server pages as a second layer.

## 4. Account management
- **Settings.** `components/dashboard/Settings.tsx` (lazy-loaded at Dashboard.tsx:11,125) contains:
  - a Cookie Preferences button
  - `<SignOutButton component="div" redirectUrl="/">` (:33-37)
  - Clerk's full `<UserProfile/>` (:39), using path routing, which is why the dashboard route is a catch-all
- **What `<UserProfile/>` provides:** name and avatar upload, adding/verifying/removing emails, linking Google, setting or changing a password, sessions and devices, MFA if enabled, and **Delete account** if enabled. Delete account triggers the webhook's `user.deleted`, which deletes the `public.users` row and cascades.
- `components/dashboard/components/UserProfile.tsx` has no Clerk code. It shows `public.users` image, name and email.
- **Deletion is incomplete today.** Nothing cancels the Paddle subscription, removes Redis catalogue keys, deletes UploadThing images or revalidates caches.
- **Replacement work:**
  - profile form: `public.users` + `auth.updateUser({data})`
  - email change: `updateUser({email})` with secure double confirmation, then copy to `public.users.email`. Paddle matches customers to users **by email** (utils/paddle/process-webhook.ts:219-223), and `users.email` is not unique.
  - password: `updateUser({password})`, plus `reauthenticate()` if secure password change is on
  - identities: `linkIdentity`/`unlinkIdentity`
  - sessions: `signOut({scope:'others'})`
  - a server delete-account route using the service-role key (`auth.admin.deleteUser`) that also handles Paddle, Redis and cache cleanup. **The app has no service-role key today.**
- **actions/users.ts helpers:**
  - `retryOperation` (:41-73): 3 attempts, 1s × attempt backoff, no retry on 23505
  - `handleUserDeletion` (:75-101): anon supabase-js delete by id
  - `sendWelcomeEmailSafely` (:103-127): email regex check, retries `sendWelcomeEmail` (actions/email.ts:37-58, Resend, from office@quicktalog.app), Sentry warning on failure

  All three are exported from a `'use server'` file, which makes them server-action endpoints.
- **Cookie consent.** For signed-in users it is stored in **Clerk publicMetadata.cookieConsent** `{analytics, essential, marketing, timestamp, version}`.
  - Write path: `utils/cookies.ts:87-106` POSTs `/api/update-consent`, which calls `auth()`, then `clerkClient().users.getUser`, then `updateUserMetadata` with the merged object.
  - CookieBanner reads it back from `useUser().user.publicMetadata` and copies it to localStorage and GTM. Signed-out users use localStorage only.
  - The DB column `users.cookie_preferences` is filled only through the Clerk `user.updated` webhook.
  - **Replacement:** write `public.users.cookie_preferences` from a session-checked route (or `auth.updateUser({data})`), read it through UserContext, and stop removing it at fetchUserData.ts:143.

## 5. Webhook sync (app/api/clerk/route.ts)
1. `verifyWebhook(req)` reads `CLERK_WEBHOOK_SIGNING_SECRET` implicitly. It races a 10s timeout (:24-35); a timeout or failed check returns 401 (:133-138).
2. Only `HANDLED_EVENT_TYPES = user.created | user.updated | user.deleted` are processed (constants/users.ts:1-5). Other events get 200.
3. The DB client is `createClient()`, which is **anon** (:51).
4. **user.created** (:58-76):
   - `buildUserData` (syncFromClerk.ts:71-113) requires a valid email. It takes `email_addresses[0]`, which is not necessarily the primary address, and lowercases it; an invalid email returns 400.
   - Row written: `{id, email, image: image_url, name: 'first last' | 'Unknown User', plan_id: DEFAULT_PLAN_ID 'pri_01k27ajepm199twd1x77rpwdrq' (syncFromClerk.ts:3, same as tiers[0].priceId.month), customer_id: null, cookie_preferences: defaultCookiePreferences}`.
   - Written with `upsert onConflict id` inside `retryOperation`.
   - Then `sendWelcomeEmailSafely` runs **without await** (:68-76). On Vercel the function can be frozen once the response is returned, so welcome emails can fail silently. The replacement should use `after()`.
5. **user.updated** (:77-79): `updateOrCreateUser` (syncFromClerk.ts:166-197) updates email, image, name and cookie_preferences.
   - cookie_preferences is taken from `public_metadata.cookieConsent`, **or reset to the default** if absent.
   - If no row was updated, it upserts one with the default plan.
6. **user.deleted** (:88-102): `handleUserDeletion` deletes the row. FK cascades remove catalogues, analytics, newsletter, ocr, prompts, user_themes and subscriptions (through customer_id).
7. **Errors:** a unique violation returns 200 (:116-123). Messages containing Database or Supabase return 500; anything else also returns 500, so Svix retries. Every write also fires the users trigger "Brevo New Contact Webhook".

**Replacement:**
- `SECURITY DEFINER` triggers on `auth.users`: AFTER INSERT creates the `public.users` row; AFTER UPDATE OF email or raw_user_meta_data syncs it.
- Deletion through FK `public.users.id → auth.users.id ON DELETE CASCADE` (needs uuid ids), plus app-side cleanup.
- Welcome email through the existing `call_edge_function_with_vault_secret` pattern, or a secret-protected route that uses `after()`.
- The on-demand sync code in fetchUserData can then be deleted.

## 8. Things that depend on how Clerk works
1. **User ids are `text` values like `user_...`.** On TEST, 3 of 3 users have them (length 32), and `auth.users` and `auth.identities` are empty.
   - FK columns pointing at `users.id` (all ON UPDATE CASCADE and ON DELETE CASCADE): catalogues.created_by, analytics.user_id, newsletter.owner_id, ocr.user_id, prompts.user_id, user_themes.user_id.
   - The ids also appear outside Postgres: in Redis catalogue JSON (`createdBy`), in public catalogue payloads, in the backend worker (analyticsProcessingJob maps name → created_by; subscriptionProcessingJob calls `/api/users/${id}`), and in the E2E account.
   - `auth.uid()` is a uuid, so the ids must be re-keyed. `UPDATE users SET id=` cascades, but Redis has to be rewritten, the Brevo trigger will fire, and all 7 columns should become uuid.
   - `get_pageview_totals` returns `user_id uuid` over a text column, so it is already broken (it is unused).
2. **Avatars are Clerk-hosted.** All 3 TEST `users.image` values are img.clerk.com URLs and will stop working once the Clerk instance is gone.
3. **Clerk infrastructure outside the code:** the `clerk.quicktalog.app` custom domain and its DNS, the Account Portal fallback for middleware redirects, emails sent by Clerk, bot protection, Testing Tokens, and a dev instance for TEST.
4. **OAuth sign-up bypasses the consent modal.** Clerk creates the account from the SignIn component, and Supabase `signInWithOAuth` will do the same.
5. **Profile field sources change.** The first email address and first/last name come from Clerk today. With Supabase, email/password users have no name unless the form collects one, and Google users have `full_name` and `avatar_url` in `user_metadata`.
6. **Existing passwords.** Keeping them requires Clerk to export bcrypt digests. Otherwise password users must reset. Google users are linked by verified email.
7. **Everyone is signed out at cutover.**

## 9. Supabase supabase-js calls break for signed-in users
Today no Supabase auth cookie exists, so `utils/supabase/server.ts` (which reads request cookies) always runs as **anon**. Once Supabase Auth cookies exist, every supabase-js call made during a signed-in request runs as **authenticated**, and `authenticated` has **no grants**. These calls will fail with "permission denied":
- app/api/dashboard/analytics/route.ts:17-25 (analytics, newsletter)
- `/api/items?type=name` fetched from the browser (hooks/useCatalogueName.ts:91 → app/api/items/route.ts:11)
- the on-demand upsert at lib/users/fetchUserData.ts:53

The Paddle and Clerk webhooks carry no user cookies, so they stay anon. `utils/supabase/server.ts:1` also has a file-level `'use server'`, which makes `createClient` a server action.

**Before cutover:** add grants or RLS policies, or move these calls to Drizzle or the service role, and remove the `'use server'` directive from that file.
