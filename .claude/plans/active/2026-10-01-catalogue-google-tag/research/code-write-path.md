# Catalogue Google tag (GA4): code audit of the write path, plans, UI, agent, metering

Audit date 2026-10-01. Question: "How the google tag and analytics will be added", meaning the concrete mechanism by which a Quicktalog owner adds a Google tag / GA4 to a catalogue and how it behaves for visitors.

**Conventions**
- Paths without a prefix are relative to `quicktalog-app/` (branch `test`, HEAD `d785bb8`, 2026-09-29). Paths starting `quicktalog-packages/` (HEAD `7a2ca85`, version 1.66.0) and `quicktalog-backend/` (HEAD `133512e`) are relative to those repos.
- **Fact** = read in code, returned by a TEST query, or measured with a live HTTP probe. **Inference** = my reasoning. **(snippet)** = taken only from a search-result excerpt.
- Nothing in the three repos was changed. PROD (`uhfbapjuzvlyzyodxhqn`) was not queried. Every TEST query was a read-only SELECT, listed in Appendix A. Live HTTP probes (Appendix B) were plain `curl` GETs of public pages. curl runs no JavaScript, so no PostHog pageview fired and no meter moved.

## 0. The answer in brief

**Fact: nothing exists today.** No column, type, action, UI, render path or plan flag for tracking exists in any repo. A grep for `integrations|measurementId|ga4|metaPixel|pixelId` finds only Sentry's `integrations:` option and pricing copy (`src/instrumentation-client.ts:25`, `src/constants/pricing.ts:79,224`). The `catalogues` table has no such column (TEST `information_schema.columns`, Q3).

**Recommended mechanism (inference, built from the facts below)**

1. **Storage.** Add a new `catalogues.integrations jsonb not null default '{}'` column. A DB `CHECK` admits only `{"ga4MeasurementId": "G-…"}` (and later `metaPixelId`).
   - It needs a column-level `UPDATE` grant to `app_user` and a column-level `SELECT` grant to `app_public` (§1).
   - Then `drizzle-kit pull`, a `@quicktalog/common` release (type `Integrations`, `defaultCatalogueData.integrations`, `features.integrations` on every tier), and an app bump.
2. **Owner write path.** A dedicated server action `updateCatalogueIntegrations(catalogueName, input)` applies the change immediately, not through draft then publish.
   - It runs: identity, Zod, plan check under the users-row lock, `UPDATE … WHERE name AND user_id … RETURNING` in one `withUser` block, then `revalidateCatalogue(name)` after the block.
   - The column stays **out of `CATALOGUE_EDITABLE_FIELDS`**, so no create, save, publish or duplicate payload can carry it.
   - It goes **into `PUBLIC_CATALOGUE_COLUMNS`**, so the ISR page can read it.
   - `readOwnedDraft` must treat it as server-owned, so a stale Redis draft cannot shadow it (§2).
3. **UI.** No fifth builder tab in v1: the tab bar is sized for exactly 4 columns at 360px. The field goes either:
   - as an "Analytics & tracking" section at the bottom of the General tab, with its own Save button and "saves immediately" copy, or
   - as a "Connect Google Analytics" card on `/admin/[name]/analytics`.
   - Plans without the feature see it under `LockedGroup` + `LimitsOverlay`, the existing lock pattern (§4).
4. **Agent.** It already cannot reach a new column: the tool schema is closed, the applier copies named fields, and the snapshot enumerates fields. Keep it that way. Add one prompt line that sends "add my Google Analytics" requests to the setting (§5).
5. **Render.** Only `src/app/catalogues/[name]/page.tsx` mounts a new client `CatalogueTracking`, and only after the new identity-free catalogue consent banner grants consent. Never the preview, the builder, `Catalogue.tsx` or a `[name]/layout.tsx`.
   - It loads `gtag/js?id=G-…&l=<own layer>` with consent defaults before `config`, and per-catalogue `cookie_prefix`/`cookie_path`.
   - Do **not** use `@next/third-parties`' `<GoogleAnalytics>`: it interpolates the ID into an inline script and drops the `l=` parameter when the data layer is renamed (§9).
6. **Visitors.** The ISR HTML is the same for everyone and carries a public ID.
   - Until the visitor accepts, nothing from Google loads, if consent mode "basic" is chosen.
   - After Accept, GA4 records `page_view` with the full URL, UTM included. Query strings do **not** fragment the ISR cache on production (measured, §6).
   - Quicktalog's PostHog-based dashboard and traffic meter keep counting independently, so the numbers will differ.

### Draft migration (not applied; tested only as SELECT expressions on TEST, Q9)
```sql
-- supabase/migrations/<YYYYMMDDHHMMSS>_catalogue_integrations.sql  (supabase migration new catalogue_integrations)
-- Owner-entered tracking IDs for the published catalogue. IDs only - never markup, URLs or snippets.
alter table public.catalogues
  add column integrations jsonb not null default '{}'::jsonb;   -- constant default: no table rewrite

alter table public.catalogues
  add constraint catalogues_integrations_check check (
        jsonb_typeof(integrations) = 'object'
    and pg_catalog.pg_column_size(integrations) < 1024
    and integrations - array['ga4MeasurementId', 'metaPixelId'] = '{}'::jsonb      -- no unknown keys
    and (not integrations ? 'ga4MeasurementId'
         or (jsonb_typeof(integrations->'ga4MeasurementId') = 'string'
             and integrations->>'ga4MeasurementId' ~ '^G-[A-Z0-9]{4,20}$'))
    and (not integrations ? 'metaPixelId'
         or (jsonb_typeof(integrations->'metaPixelId') = 'string'
             and integrations->>'metaPixelId' ~ '^[0-9]{15,16}$'))
  );

-- UPDATE is column-level for app_user (20260921181104:55-57): the new column must be named or every write is 42501.
grant update (integrations) on public.catalogues to app_user;
-- SELECT is column-level for app_public (20260921181104:58-60): needed because the ISR page reads it.
grant select (integrations) on public.catalogues to app_public;
```

**Fact (Q9):** the CHECK expression, run as a SELECT over literal jsonb on TEST (PostgreSQL 17):
- **accepts:** `{}`, a GA4 ID, GA4 plus Pixel;
- **rejects:** lowercase `g-…`, `GTM-…`, a quote-and-script payload, a JSON array, a numeric ID, an unknown `headCode` key.

The app must therefore upper-case and trim before saving.

Two design notes:
- **Shape.** Typed text columns (`ga4_measurement_id text check (…)`) would be the alternative. jsonb keeps the grant set to one column, but each new vendor still needs a migration to widen the CHECK. That is acceptable, because a vendor also needs code, CSP and a package release.
- **Scope.** If Meta Pixel is not in v1, drop its line.

### Deployment ordering (critical)
- **Fact.** Drizzle's bare `select()` and `.returning()` list every column the schema object knows.
  - `loadOwnedCatalogue` (`src/lib/catalogue/draft-cache.ts:26-31`) serves the builder, preview, save and publish.
  - `duplicateItem` selects at `src/actions/catalogue.ts:186-190`. `createCatalogue`, `publishCatalogue` and `duplicateItem` call `.returning()` at :289, :449 and :222.
  - `getPublicCatalogue` selects `PUBLIC_CATALOGUE_COLUMNS` (`src/lib/catalogue/public.ts:23-32`).
- **Inference: if the app ships the new package before PROD has the column**
  - Every builder load, save and publish fails with 42703 (undefined column).
  - If `PUBLIC_CATALOGUE_COLUMNS` includes `integrations` before PROD has the `app_public` grant, `getPublicCatalogue` fails with 42501. `/api/items/[name]` then answers 500 (`src/app/api/items/[name]/route.ts:26-35`). The page does not call `notFound()` for a 500: it renders `<LimitsModal type="notFound">` (`src/app/catalogues/[name]/page.tsx:125-150`), and ISR can keep serving that render for up to 24h (`page.tsx:11`).
  - So the migration must reach TEST, then PROD, **before** the app version that reads the column is deployed to each environment.
  - The migration is backward compatible: it is additive with a constant default, and old code's explicit column lists simply omit it.
- **Facts on PROD lagging TEST.**
  - The PROD showcase `montre-shop` still renders `type: "category"` blocks, the pre-`20260926130000` key (probe B3).
  - The PROD response carries no CSP header at all, while TEST carries `Content-Security-Policy-Report-Only` (probe B2).
  - **Inference:** PROD's database and deployment are behind `test`. The pending migrations must be applied in order before this one.

### Skill rules a new `updateCatalogueIntegrations` must follow
From `.claude/skills/server-action-and-route/SKILL.md` and `.claude/skills/data-revalidation/SKILL.md`:
1. **Identity first.** `getVerifiedIdentity()` inside the action. Never take `userId` as an argument; helpers that take one live in `server-only` `src/lib/` modules (server-action SKILL.md:88). `"use server"` files export only actions (`.claude/CLAUDE.md`).
2. **Exactly one block** per action: `withUser(me, tx => …)`. Never `asAdmin` (an architecture test fails the build: SKILL.md:36). The block is the only DB path, and a stray query fails with 42501 (SKILL.md:28-34).
3. **Owner predicate** `eq(catalogues.userId, me.userId)` in the statement, even though RLS enforces it (SKILL.md:89).
4. **Check what came back:** `.returning(...)`, and zero rows means not found (SKILL.md:90).
5. **Trust nothing from the client.** The plan comes from `users.plan_id` via `getPlanForUpdate` (`src/lib/entitlements/plan.ts:27-38`, which locks the row `for no key update`), never from the UI (SKILL.md:91; `.claude/CLAUDE.md`).
6. **Short transaction.** No Redis, fetch or `revalidate*` inside the block (SKILL.md:92).
7. **Revalidate after the block.** `revalidateCatalogue(name)` because the published page changes. `revalidateDashboard()` is not needed: no counts change (data-revalidation SKILL.md:34-44). The server action owns invalidation; the client only re-renders (SKILL.md:12-14).
8. **Catch.** `Sentry.captureException(err, { tags: { op } })` + `console.error` (SKILL.md:94).
9. **Return shape.** A result object `{ success, data?, error? }` with an explicit return type, because the UI needs a message and the repo runs `strict: false` (SKILL.md:96-100).
10. **Draft sync.** The skill says "write or delete the draft on every write" (data-revalidation SKILL.md:67). Here the cleaner rule is that the draft never holds this field (see below).

Two skill items are stale:
- data-revalidation SKILL.md:58-60 says `src/app/api/items/route.ts` writes `catalogues` via Supabase. That route is GET-only through `withPublic` (`src/app/api/items/route.ts:10-26`).
- The server-action skill's sample maps no error codes. Copy the QR action's mapping style, not its semantics (below).

### Draft-then-publish vs apply-immediately

| | Draft then publish (add to `CATALOGUE_EDITABLE_FIELDS`) | **Apply immediately (dedicated action) - recommended** |
|---|---|---|
| Write paths to guard | create (:277-289), Save→Redis (:351), publish (:437-449), duplicate (:201-222). Each needs validation, or the value lands in an inline script (§9) | One action, plus the DB CHECK as a backstop |
| Plan gate | Must be added to `applyPlanToCatalogue` (`entitlements/catalogue.ts:13-28`), which runs on create, update and publish | One check in the action |
| Owner over the traffic limit | Cannot change or **remove** the tag: publish refuses when `canActivate` fails (`actions/catalogue.ts:430-431`) | Remove is always allowed |
| Coupling | Changing the ID forces publishing every pending content edit in the draft | Independent of content drafts |
| Redis draft | Holds the ID, so it is part of the draft model | Must be kept out: see below |
| Precedent | All builder panel fields | `upsertQrConfig`, which saves immediately (`src/actions/qr-configs.ts:15-69`; `docs/architecture/qr-codes.md:36-50`) |
| Live effect | Only at the next Publish | Immediately for active catalogues (`revalidateCatalogue`); from publish onwards for drafts (app_public sees only `active`, Q5) |

**Inference:** apply immediately. Its consequences in this codebase:
- **Keep the column out of `CATALOGUE_EDITABLE_FIELDS`.** `createCatalogue` then always inserts the DB default `{}`.
  - `publishCatalogue` can never write it, even though the client sends the whole `Catalogue` object.
  - `duplicateItem` will not copy it. Whether a duplicate should inherit the owner's GA ID is a product choice; copying it needs an explicit, plan-checked line.
- **Add `integrations` to the server-owned list in `readOwnedDraft`** (`draft-cache.ts:61-71`) and strip it in `writeOwnedDraft` (:75-82). Otherwise:
  - the full client object written by Save (`actions/catalogue.ts:351`) or the published row written after Publish (:455) puts a copy into Redis;
  - `{...row, ...draft}` (:61-63) then shows that stale copy in the builder after the dedicated action changed the row.
  - It would never reach the public page (publish filters it), but the editor would lie.
- **After the action succeeds**, the client updates context state with the returned value (`updateCatalogue({ integrations })`, `src/context/CatalogueContext.tsx:87-91`) so the panel reflects it.
- **`updated_at`.** Every write bumps it through `catalogues_touch_updated_at` (Q6). `applyPlanDowngrade` ranks catalogues by `updated_at desc` to decide which stay active (`src/lib/entitlements/catalogue.ts:42-57`), so saving tracking slightly favours that catalogue. This is minor.
- **Optional belt and braces.** `publishCatalogue` and `updateItemStatus` (re-activation, `actions/catalogue.ts:145-152`) could force `integrations: {}` when the tier lacks the feature, like `applyPlanToCatalogue` does for branding. That closes the paid-to-paid downgrade gap at the next write (§3).

### Action sketch (inference; pattern copied from `src/actions/qr-configs.ts`)
```ts
"use server"; // src/actions/integrations.ts - exports only this action
export async function updateCatalogueIntegrations(
  catalogue: string, input: unknown,
): Promise<{ success: boolean; data?: Integrations; error?: string }> {
  try {
    const me = await getVerifiedIdentity();                       // 1. identity
    if (!me) return { success: false, error: "Unauthorized" };
    if (typeof catalogue !== "string" || catalogue.length > 200)
      return { success: false, error: "Catalogue not found" };
    const parsed = integrationsSchema.safeParse(input);           // src/constants/schemas.ts; strips unknown keys
    if (!parsed.success) return { success: false, error: "Enter the measurement ID that starts with G-" };
    const next = parsed.data;                                     // {} = remove
    const out = await withUser(me, async (tx) => {                // 2. one short block
      const tier = await getPlanForUpdate(tx, me);                // users row locked
      if (Object.keys(next).length > 0 && !allowsTracking(tier)) return { locked: true as const };
      const [row] = await tx.update(catalogues).set({ integrations: next })
        .where(and(eq(catalogues.name, catalogue), eq(catalogues.userId, me.userId)))   // 3. owner predicate
        .returning({ name: catalogues.name, integrations: catalogues.integrations });  // 4. check rows
      return row ? { row } : null;
    });
    if (!out) return { success: false, error: "Catalogue not found" };
    if ("locked" in out) return { success: false, error: "Your plan does not include Google Analytics" };
    revalidateCatalogue(out.row.name);                            // 7. after the block
    return { success: true, data: out.row.integrations as Integrations };
  } catch (err) {
    const pg = pgError(err);
    if (pg?.code === "23514" && pg.constraint === "catalogues_integrations_check")
      return { success: false, error: "That ID is not valid" };   // DB backstop, not a Sentry event
    Sentry.captureException(err, { tags: { op: "updateCatalogueIntegrations" } });
    console.error("Unexpected error while saving tracking settings:", err);
    return { success: false, error: "Failed to save" };
  }
}
```
**Do not copy the QR action's mapping of 42501 to "not found"** (`qr-configs.ts:55-57`). That mapping exists because an upsert on another owner's row raises 42501. For this plain UPDATE, a foreign row yields 0 rows, so a 42501 can only mean a missing column grant, which is a deployment bug that must reach Sentry.

An optional rate-limit rule fits the existing table (`src/lib/rate-limit.ts:8-19`), because each save purges every catalogue's `catalogue-detail` cache (above).

## 5. AI agent: the new field stays unreachable

## 6. Analytics, metering and QR codes

### Facts: what feeds Quicktalog's own numbers
- **PostHog** is initialised on every route with `capture_pageview: true`, autocapture off and recording off, with no consent option (`src/instrumentation-client.ts:5-19`). It is proxied through `/ingest` (`next.config.ts:71-85`).
- **The owner analytics page** queries PostHog live, matching `$host` = host of `NEXT_PUBLIC_BASE_URL` and `$pathname in ('/catalogues/<name>', '/catalogues/<name>/')` (`src/lib/analytics/catalogue-traffic.ts:30-36,51-66`).
  - So `?utm_*`, `fbclid` and `#fragment` are counted (`docs/architecture/analytics.md:65`).
  - `/preview` is excluded.
- **The worker's daily job** (`quicktalog-backend/src/handlers/analyticsProcessingJob.ts`), cron `0 3 * * *` (`quicktalog-backend/wrangler.jsonc:50`), scheduled at `src/index.ts:33-42`:
  - The HogQL filters `event = '$pageview'`, `$current_url NOT ILIKE '%admin%'`, `LIKE '%/catalogues/%'`, not localhost, and `ILIKE '%www.quicktalog.app%'` on prod or `'%test.quicktalog.app%'` on test. It groups by `toDate(timestamp), current_url` (`quicktalog-backend/src/utils/analytics.ts:1-27`).
  - The slug comes from `/\/catalogues\/([^/?#]+)/` (:85-86). URL variants are summed per catalogue per day (:111-145), so **query strings fold into the right catalogue**, but `unique_visitors` becomes an upper bound (`docs/architecture/analytics.md:30`).
  - Rows are upserted with `onConflict: "catalogue_id,day", ignoreDuplicates: true` (:147-154).
- **Readers of the `analytics` table:** `private.my_usage()` (dashboard meters and `canActivate`) and the worker's traffic enforcement, which deactivates every active catalogue of a **non-Starter** user over `traffic_limit` (`quicktalog-backend/src/handlers/subscriptionProcessingJob.ts:54-58,74-89`).
- **Quicktalog's own tags on catalogue pages.**
  - `<ClarityScript />` and `<GoogleTagManager gtmId={process.env.GTM_ID} />` sit in the root layout head (`src/app/layout.tsx:46-49`). GTM uses the default `dataLayer`: no `dataLayerName` is passed, and `@next/third-parties` appends `&l=` only when one is (`node_modules/@next/third-parties/dist/google/gtm.js:17,38`).
  - The cookie banner returns early on any `/catalogues/` path (`src/components/general/CookieBanner.tsx:28-37`) and reads identity (`:22`). Its "consent" events are custom dataLayer events, not `gtag('consent', …)` (`src/utils/cookies.ts:36-71`).
  - PROD HTML of `montre-shop` contains the `gtm.js` loader (probe B3).

### Facts: query strings and ISR (live probes, 2026-10-01, Appendix B)
- `https://www.quicktalog.app/catalogues/montre-shop` with never-seen query strings (`?utm_source=qr&utm_campaign=probe-<random>`, the same with a `-b` suffix, `?fbclid=probe<random>`) returned **`x-vercel-cache: HIT` with the same increasing `age`** (18, 19, 20, 21, 22 s) as the bare URL, `x-matched-path: /catalogues/montre-shop`, `x-nextjs-prerender: 1`. **Query strings are not part of the ISR cache key in production** (probe B1).
- One earlier UTM request returned `STALE` with age 28026. The `x-vercel-id` shows `fra1::iad1`, and the next request was a `HIT`. **Inference:** a not-yet-revalidated regional copy, not a separate cache entry.
- Why this holds:
  - The page never reads `searchParams`; it receives only `params` (`page.tsx:106`). Next.js documents that using `searchParams` "will opt the page into dynamic rendering" ([Next.js page.js](https://nextjs.org/docs/app/api-reference/file-conventions/page)).
  - Vercel's prerender config caches each listed query parameter separately via `allowQuery`; "If an empty array, query values are not considered for caching" ([Vercel Build Output API](https://vercel.com/docs/build-output-api/primitives)). The probe shows the effective behaviour.
- PROD is fronted by Cloudflare (`server: cloudflare`, `cf-cache-status: DYNAMIC`, i.e. no HTML caching there) before Vercel (probe B2).

### QR codes: can they carry UTM?
- **Fact:** not today. `catalogueUrl()` returns `${NEXT_PUBLIC_BASE_URL}/catalogues/${catalogue}` (`src/lib/qr/design.ts:143-146`). The editor overwrites `data` with it on load (`loadQrConfig`, :177-201) and the action on save (`normalizeQrConfig`, :214-221; `src/actions/qr-configs.ts:33-37`). "The URL is pinned" (`docs/architecture/qr-codes.md:34`).
- **Inference: the change**
  - Give `catalogueUrl()` an optional server-chosen suffix such as `?utm_source=qr&utm_medium=print&utm_campaign=<slug>`, chosen from a fixed list, never free text, so the pinning rule stays intact.
  - Google says to "always use utm_source, utm_medium, and utm_campaign" ([GA help](https://support.google.com/analytics/answer/10917952?hl=en)). Without them a QR scan has no referrer and GA4 cannot attribute it.
  - Printed codes already in the wild keep working: the plain URL remains valid.
  - A longer URL raises the QR version (density). The editor already shows the version and a scan-risk check (`src/lib/qr/version.ts`, `src/lib/qr/scan-risk.ts`).
- **Effects on ISR and metering:**
  - ISR is unaffected (measured above).
  - Pageviews, the input to the traffic limit, are unaffected (`slugOf` stops at `?`; the app's analytics page matches `$pathname`).
  - `unique_visitors` in the `analytics` rollup is further inflated when one visitor hits both the UTM and the bare URL (summing, :111-145).
  - Ad click IDs (`fbclid`, `gclid`) are unique per click, so they multiply the `(date, current_url)` groups the worker pulls (`LIMIT 1000000`, `analytics.ts:25`).

### What must not break if Quicktalog's own scripts change on catalogue pages (inference)
1. **PostHog `$pageview` on `/catalogues/<slug>` is load-bearing.** It feeds both the owner analytics page and the traffic meter that gates publishing (`canActivate`) and deactivates catalogues (the worker).
   - If the new consent banner also gates PostHog, the meter and owner stats drop to consenting visitors only.
   - Any change to Quicktalog's own tags must keep PostHog unconditional (a legal question for the consent research) or move metering to a server-side count.
2. **Domain and path coupling.** The worker filters on `www.quicktalog.app` / `test.quicktalog.app` in the full URL (`analytics.ts:6-7`). The app matches `$host` from `NEXT_PUBLIC_BASE_URL` (`catalogue-traffic.ts:56`). QR codes pin `NEXT_PUBLIC_BASE_URL/catalogues/…` (`design.ts:144-146`), and the CRM views build `https://www.quicktalog.app/catalogues/` URLs (`quicktalog-packages/src/drizzle/migrations/schema.ts:254,263`). Serving catalogues from a separate domain, the precondition for GTM, has to update all of these together.
3. **Shared data layer.** Quicktalog's GTM uses `window.dataLayer`.
   - A customer gtag on the same data layer would share Consent Mode state and command queue with Quicktalog's container.
   - The customer tag must use its own layer (`gtag/js?id=…&l=<name>`; [Google: rename the data layer](https://developers.google.com/tag-platform/devguides/datalayer#rename_the_data_layer)) and a namespaced function, not a global `gtag`.

### Pre-existing worker issues found while tracing the meter (facts in code; impact is inference; not verifiable on TEST, which has 0 analytics rows and 0 job logs, Q8)
- **`NOT ILIKE '%admin%'` runs on the whole URL** (`analytics.ts:17`). Any catalogue whose slug contains "admin" (for example `badminton-club`) and any URL whose query contains "admin" is dropped from the meter.
- **`/catalogues/<slug>/preview` passes `LIKE '%/catalogues/%'`,** and `slugOf` maps it to the slug (:85-86). Owner previews therefore count toward the traffic meter, while the owner analytics page excludes them.
- **Daily rows are first-write-wins.** The daily window is the 24h before 03:00 UTC (`analyticsProcessingJob.ts:13-25`), grouped by `toDate(timestamp)`, and upserted with `ignoreDuplicates: true` (:147-154). Each day's row is written by the first run that sees part of that day (00:00-03:00) and never updated by the next run.
  - **Inference:** stored daily pageviews may cover only about 3 of 24 hours, so the meter undercounts.
  - Verify on PROD (read-only, with approval) by comparing a day's `analytics.pageviews` against PostHog for the same catalogue and day.

### Drafted PROD audit query (NOT run; syntax validated on TEST with 0 rows, Q11; regexes self-tested on literal snippets, Q12)
```sql
-- READ-ONLY. Run on PROD (uhfbapjuzvlyzyodxhqn) only with the founder's explicit go-ahead.
-- Lists every block that carries a Google tag, GTM or Meta Pixel snippet, with the owner to contact.
with blocks as (
  select c.id as catalogue_id, c.name, c.status, c.user_id, c.updated_at,
         b.ordinality as position,
         b.value->>'type' as block_type,
         coalesce(b.value->>'code', b.value->>'content', '') as body
    from public.catalogues c
   cross join lateral jsonb_array_elements(
           case when jsonb_typeof(c.content) = 'array' then c.content else '[]'::jsonb end
         ) with ordinality as b(value, ordinality)
),
hits as (
  select bl.*,
         bl.body ~* '(gtag\(|googletagmanager\.com/gtag/js)'                                  as has_gtag,
         bl.body ~* '(googletagmanager\.com/gtm\.js|GTM-[A-Z0-9]{4,})'                        as has_gtm,
         bl.body ~* '(fbq\(|connect\.facebook\.net/[a-z_]+/fbevents\.js|facebook\.com/tr\?)'  as has_meta_pixel,
         array(select distinct m[1] from regexp_matches(bl.body, '\m((?:G|AW|GT|DC)-[A-Z0-9]{6,})', 'g') as m) as google_ids,
         array(select distinct m[1] from regexp_matches(bl.body, '\m(GTM-[A-Z0-9]{4,})', 'g') as m)           as gtm_ids,
         array(select distinct m[1] from regexp_matches(bl.body, 'fbq\(\s*[''"]init[''"]\s*,\s*[''"]?([0-9]{10,20})', 'g') as m) as pixel_ids
    from blocks bl
   where bl.block_type in ('custom_code', 'embedding', 'text')
)
select h.name as catalogue, h.status, u.email as owner_email, p.name as plan, h.updated_at,
       h.position, h.block_type, h.has_gtag, h.has_gtm, h.has_meta_pixel,
       h.google_ids, h.gtm_ids, h.pixel_ids,
       left(regexp_replace(h.body, '\s+', ' ', 'g'), 160) as excerpt
  from hits h
  join public.users u on u.id = h.user_id
  left join public.plans p on p.id = u.plan_id
 where h.has_gtag or h.has_gtm or h.has_meta_pixel
    or (h.block_type in ('custom_code', 'embedding') and cardinality(h.google_ids) > 0)
 order by (h.status = 'active') desc, h.updated_at desc;
```

**Regex self-test (Q12):**
- A gtag snippet yields `has_gtag` and `G-PSW1MY7HB4`; a GTM snippet yields `has_gtm` and `GTM-AB12CD3`; a Pixel snippet with its noscript image yields `has_meta_pixel` and `123456789012345`; an Ads snippet yields `AW-123456789`.
- A text block "G-STAR RAW … AW-2026" produces no IDs, thanks to the 6-character minimum and the code-block restriction.
- **Limits:** Redis drafts (unpublished snippets) are not in Postgres. Block age is not stored, so `updated_at` is only a hint of whether a snippet predates the sandbox switch (`e87e1f2`, 2026-09-15, confirmed by `git show`).

## 9. Render path: facts the implementer must know (for completeness; consent design is out of scope here)

- **Where to mount.**
  - `src/app/catalogues/[name]/page.tsx:143-147` renders `<Catalogue item type="view">` for active rows. That is the only place to add `<CatalogueTracking integrations={item.integrations} slug={item.name} />`.
  - The preview renders the same `<Catalogue type="view">` from the owner's draft (`preview/page.tsx:31-36`), and `Catalogue.tsx` is shared by edit, view and demo (`src/components/catalogue/view/Catalogue.tsx:35-44`). Neither may host the tag.
  - The catalogue route has no layout file (`ls src/app/catalogues/[name]`: `page.tsx`, `error.tsx`, `preview/`), and a `[name]/layout.tsx` would also wrap `/preview`.
- **Do not use `@next/third-parties` `GoogleAnalytics`** (installed 15.5.26). Facts in `node_modules/@next/third-parties/dist/google/ga.js`:
  - `gaId` is interpolated unescaped into an inline script, `gtag('config', '${gaId}' …)` (:36). Without strict validation that is a script-injection sink on the builder's origin.
  - When `dataLayerName` is changed, the script `src` is still `gtag/js?id=${gaId}` with **no `&l=`** (:37). Google requires the `l` parameter for a renamed layer ([Google](https://developers.google.com/tag-platform/devguides/datalayer#rename_the_data_layer)), so the renamed queue would not be read (inference).
  - It sets no consent default.
  - The sibling `GoogleTagManager` does append `&l=` (`gtm.js:17`).
- **Consent ordering.** Google: call `gtag('consent', 'default', …)` "before any commands that send measurement data (such as config or event)" ([Google consent mode](https://developers.google.com/tag-platform/security/guides/consent)). Whether gtag.js loads before consent ("advanced", with cookieless pings) or only after ("basic") is the consent research's call. "Basic" is the conservative EU default (inference).
- **Cookies on a shared origin.**
  - GA4's `cookie_domain` defaults to `'auto'`, the eTLD+1, and `cookie_path` to `'/'`; `page_location` defaults to `document.location` ([GA4 config reference](https://developers.google.com/analytics/devguides/collection/ga4/reference/config)).
  - **Inference:** every customer's tag on `www.quicktalog.app` would write `_ga` on `quicktalog.app` (visible to `test.quicktalog.app` too). It would share one client-id cookie across all catalogues and with Quicktalog's own GA if its container uses GA4 defaults.
  - Set `cookie_prefix` per catalogue (the option exists: (snippet) same page) and `cookie_path: '/catalogues/<slug>'`. Slugs are safe to interpolate because of `catalogues_name_slug` (Q4), but use `JSON.stringify` anyway.
- **CSP** (Report-Only today: `next.config.ts:48-69`; PROD sends no CSP header, probe B2). Google's list for GA without Ads:
  - `script-src-elem https://www.googletagmanager.com`;
  - `img-src https://www.googletagmanager.com https://*.google-analytics.com`;
  - `connect-src https://www.googletagmanager.com https://*.google-analytics.com https://*.google.com`.
  - With Ads features add `*.g.doubleclick.net`, `*.google.<TLD>`, `pagead2.googlesyndication.com` and `frame-src https://www.googletagmanager.com` ([Google CSP guide](https://developers.google.com/tag-platform/security/guides/csp)).
  - Current `connect-src` lacks `https://*.google.com` (`next.config.ts:55`), and `frame-src` lacks googletagmanager (:56). Both must be added before the CSP is ever enforced.
- **Why accept `G-` and refuse `GTM-`.**
  - Google tag IDs include `GT-`, `G-` and `AW-` ([Google tag ID](https://support.google.com/tagmanager/answer/12326985?hl=en)), and a GA4 measurement ID is "G-" followed by letters and numbers, e.g. `G-PSW1MY7HB4` ([GA4 measurement ID](https://support.google.com/analytics/answer/12270356?hl=en)).
  - Google tag settings are a fixed list of Google-defined options: domains, internal traffic, unwanted referrals and so on ((snippet) [Configure your Google tag settings](https://support.google.com/tagmanager/answer/12131703?hl=en)).
  - A GTM container can run "your own custom HTML or JavaScript code" ([GTM custom tags](https://support.google.com/tagmanager/answer/6107167?hl=en)).
  - **Inference:** a validated `G-` ID cannot become arbitrary first-party JavaScript on the builder's origin; a `GTM-` ID can.
  - `AW-`/`GT-` could come later with the Ads CSP hosts and ad-consent signals.
