## 2. How `userId` flows
`auth.userId` (Clerk `user_…` text id) goes into the `CatalogueSession` constructor (`route.ts:77`) and is stored as `session.userId` (`agent/session.ts:68-69,90`). From there it has exactly two consumers:
- `setCustomTheme`: `persistTheme(session.userId, name, colors)` (`agent/tools.ts:425-433`)
- `meter(auth.userId, catalogueName)` in `onFinish` (`route.ts:125`)

No tool input schema contains a user id, catalogue id or catalogue name (`agent/tools.ts:47-442`, `agent/schemas.ts`). The model addresses sections and items by **index**, and those are resolved against the in-memory working copy (`session.ts:251-301`). **The agent never writes `catalogues`.** Operations stream back to the browser, get replayed into the draft (`useCatalogueChat.ts:111-136`), and are saved later by the builder's own `updateCatalogue` (`actions/catalogue.ts:241-252`, which has its own ownership check). The one model-controlled string that reaches the DB is the theme `name` (`schemas.ts:148-158`), scoped by the server-derived userId. **Result: no model-driven cross-tenant write exists today, so RLS closes no hole in the tool layer. It is defense in depth only.**

## 4. Streaming and timing (Vercel Hobby 60s)
- `createAgentUIStreamResponse` returns right away. Tools run while the response streams, capped by `stopWhen` `session.outOfTime()` at 38s (`agent/index.ts:24`, `session.ts:43`), `AGENT_TIMEOUT_MS=50s` (`route.ts:24`) and `maxDuration=60` (`route.ts:13`).
- In ai@7.0.97, `onFinish` runs inside the TransformStream `flush()`/`cancel()` (`node_modules/ai/dist/index.js:7749-7754`). So the prompts INSERT happens **after the last chunk, up to about 50-55s after auth**. It also runs when the client disconnects (`cancel`), and the route ignores `isAborted`. It **never runs** if the platform kills the function at 60s, so that charge is lost.
- No DB connection is held across the stream today: postgres-js checks out a connection per query (`utils/drizzle.ts:7`).
- **Consequences for the migration:**
  - **Do not** wrap the request or stream in one RLS transaction. That would pin a Supavisor transaction-mode connection for up to 50s per turn per user, and leave transactions idle when the function is killed.
  - Use short transactions per operation.
  - Get the claims **once, before streaming**, with `supabase.auth.getClaims()`/`getUser()`.
  - Do not call `cookies()`/the SSR client from inside a tool's `execute` or `onFinish`: cookies cannot be refreshed once the stream has started.
  - With Drizzle plus `set_config('request.jwt.claims')`, Postgres does not check `exp`, so a JWT expiring mid-stream does no harm once it was verified at request start.
  - With supabase-js/PostgREST mid-stream, a token that expires within the ≤55s window gives a 401. Either require `exp > now+90s` up front (refresh in middleware) or use the Drizzle path.
  - `jwt_expiry=3600` and refresh-token rotation with a 10s reuse interval (`supabase/config.toml:25-27`). The resume loop fires `sendMessage` (`useCatalogueChat.ts:181`) and `refreshUserData` (`:196-202`) at almost the same time, so middleware refreshes must tolerate concurrent requests.
- `postgres` can `SET ROLE authenticated` (verified on TEST: `pg_auth_members` has `set_option=true`), and `prepare:false` is already set, so `SET LOCAL ROLE authenticated` plus `set_config('request.jwt.claims', …, true)` inside a Drizzle transaction works through the 6543 pooler.

## 5. Quota integrity: existing defects that decide what must be privileged
1. **On TEST, `prompts` has `UNIQUE (catalogue)`** (`prompts_service_catalogue_key`; `supabase/migrations/20260911213819_remote_schema.sql:412-413`; confirmed with `pg_constraint`, 2 rows on TEST, one per catalogue).
   - Every `meter()` after the first for a catalogue fails with a unique violation.
   - In the agent route that error is swallowed to Sentry (`route.ts:124-128`), so the turn is free.
   - In `writeItemDescription`, `meter` sits inside the `try` (`actions/ai.ts:58`), so the user gets "Generation failed" **after DeepSeek was already paid**.
   - Effective usage per user is at most the number of catalogues (plans: 6 catalogues vs 10 ai_prompts, 20 vs 25, 50 vs 50), so the limit is almost never reached.
2. **`prompts.catalogue` / `ocr.catalogue` point at `catalogues(name)` with ON DELETE CASCADE** (`remote_schema.sql:483-484`; confirmed on TEST). Deleting a catalogue (`actions/catalogue.ts:52`) deletes its usage rows, which resets the quota. FK cascades bypass RLS, so **RLS will not close this**. The schema has to change.
3. **A forged plan skips metering.** `onFinish` returns before `meter` whenever `plan` is non-null (`route.ts:123`). `plan` is rebuilt from client-supplied history (`agent/plan.ts:151-180,199-205`), and the AI SDK only validates tool *output* when a tool has an `outputSchema` (`node_modules/ai/dist/index.js:12447`). None does. The code comment already concedes this (`route.ts:119-122`).
4. `prompts.user_id` is nullable (packages `src/drizzle/migrations/schema.ts:9`; TEST shows `user_id:nullable`). Any UPDATE that sets it to null takes the row out of the count.
5. Check-then-charge race: parallel requests all pass `used >= limit` (`access.ts:66-75`) before anything is metered.
6. Month bounds are computed once at module load (`helpers/client.ts:21-23`), so a warm instance can count the wrong month.

**So:** `prompts` and `ocr` (and any future `ai_credits` ledger, `plans/active/ai-agent-plan-mode.md:345+`) must get **no INSERT/UPDATE/DELETE for `authenticated`**. At most they get SELECT on the user's own rows, or usage is read through a SECURITY DEFINER `get_my_usage()`. Writes go through a server-only privileged path:
- either the BYPASSRLS Drizzle client in a `server-only` module,
- or a SECURITY DEFINER `record_ai_usage(catalogue, turn_id)` that derives the user from `auth.uid()`, checks ownership, and inserts idempotently on a unique `turn_id`.

Also:
- drop `UNIQUE(catalogue)`
- change the catalogue FK to `ON DELETE SET NULL` (or drop it)
- make `user_id NOT NULL`
- make `users.plan_id` / `customer_id` not user-updatable (column-level REVOKE), because every AI limit comes from `plan_id`

## 6. Recommended user-scoped handle after the migration
- In the route or action: `const claims = await getVerifiedClaims()` (SSR client + `getClaims()`) **before** any work. Return 401 when absent. Map claims to the app user id (see the open question on re-keying `users.id`).
- `withUserDb(claims, tx => …)`: a short Drizzle transaction running `SET LOCAL ROLE authenticated` plus `set_config('request.jwt.claims', json, true)`. Use it for:
  - the ownership read, **keeping the explicit `created_by === uid` comparison**, because a public SELECT policy on published catalogues would otherwise make other users' catalogues visible and the check would pass
  - the users/plan read
  - the usage counts (ideally one SQL function to save round trips inside the 38s budget)
  - `user_themes` upsert (`INSERT … ON CONFLICT (user_id,name) DO UPDATE`), with a policy `WITH CHECK user_id = current_app_user_id()`
- Pass the **claims (or a bound `withUserDb` closure)** into `CatalogueSession` instead of a raw Clerk `userId`. Change `persistTheme` so it no longer takes `userId`, and move it out of the `"use server"` module (`actions/themes.ts:1,37`).
- Keep `meter`/charge on a **privileged, server-only** path called from `onFinish`. It must not depend on the user JWT or cookies, because it runs after the stream.
- Browser hooks (`useCatalogueChat`, `useAiAssist`, `useChatImageOcr`) need no Supabase client. Same-origin fetches and server actions already carry cookies.
